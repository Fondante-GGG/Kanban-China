# ADR-0002: монолит для текущего выполнения ТЗ

Дата: 31.10.2026.
Статус: принято по явному последующему указанию пользователя.
Заменяет: ADR-0001 в части обязательного микросервисного старта.

## Контекст и решение

Пользователь уточнил: «пусть пока что будет монолит потом только микросервис».
Это соответствует стартовой стратегии ТЗ (монолит на первой фазе и модульный
монолит с PostgreSQL). Продолжаем функциональные требования ТЗ в существующем
Django backend с общей ORM/БД и локальными транзакциями. Перепись уже готовых
модулей и микросервисная декомпозиция не требуются перед следующей функцией.

BE-01 определяет модуль-владелец, инварианты, зависимости и API до реализации;
FE-01 подтверждает интеграцию, UX-01 готовит handoff, CR-01 отдельно проверяет
код. Границы domain/application/infrastructure/presentation и модулей сохраняются.
Разрешены существующие межмодульные ORM-связи и транзакции в общей БД монолита;
они не дают права обходить проверки или писать в действительно внешние БД.

Не создавать искусственные внутренние HTTP-вызовы, отдельные БД, брокер или
контейнеры ради будущей микросервисности. Документировать реальные внешние API
через OpenAPI, события — версионированными схемами, когда они вводятся.
Outbox/inbox и retry/DLQ использовать по реальной необходимости доставки.

## Позднейший переход

Микросервисы остаются возможным следующим этапом, а не текущим условием готовности.
Для него отдельно потребуются разрешение пользователя, границы владения данными,
API/event-контракты и миграционный план с backup/restore и rollback. Этот ADR
не разрешает перенос данных, изменение денежных/складских правил или deploy.

## Последствия

- Команда может продолжать функции ТЗ в текущем монолите без архитектурной паузы.
- Готовность функции не зависит от наличия отдельных сервисов или БД.
- Авторизация, аудит, идемпотентность, целостность остатков, локализация,
  проверки и независимое ревью остаются обязательными.
- История ADR-0001 сохраняется, но противоречащие ему требования заменены этим решением.
