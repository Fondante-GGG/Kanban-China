# ADR-0007: заявка, последовательное согласование и точный платёж

Статус: технический контракт TL/BE/FE подтверждён, реализация проходит ревью.
Основание: ТЗ Г.6 (без утверждённой заявки оплата запрещена), Г.1 (маршруты),
ADR-0002 монолит, ADR-0006 закрытый период.

## Граница

Заявка на оплату одной задолженности в её валюте содержит счёт, точную сумму,
плановую дату и основание. Один утверждённый документ разрешает один точный
платёж; частичный долг погашается несколькими заявками. Утверждение не резервирует
деньги и не создаёт платёж. При исполнении остаток долга/банк/валюта/период
проверяются повторно под блокировками. Межвалютный расчёт, платёжные лимиты и
новые пороги согласования не вводятся.

Переиспользуется настраиваемый последовательный маршрут business_type
finance_payment_request. Без конфигурации submit409, без fallback директора.
Все назначенные участники фиксируются в snapshot; решение доступно только
текущему назначенному активному участнику с approval.read+act. Автор не может
утвердить свою заявку даже как директор. Изменение полей/submit/cancel доступны
только создателю с payment.manage: иной исполнитель не может переписать чужую
заявку и затем согласовать собственное изменение. Proof и исполнение не
изменяют утверждённые сумму/счёт/дату. Возврат открывает исправление, новая
подача создаёт новый snapshot/approval. Отклонение и отмена терминальны.
Параллельные/условные маршруты, замещения и расширение всего движка отдельно.

## Данные и конфиденциальность

Создание имеет UUID и первоначальный неизменяемый creation_payload: повтор
потерянного ответа остаётся распознаваемым после редактирования черновика.
При платеже OneToOne на заявку и exact signature дают повтор200 без второго
списания. Другой payload409. Исторические платежи остаются с nullable request/proof,
фиктивные утверждения и файлы не добавляются.

Proof — фактический приватный PDF/JPEG/PNG/WebP, не публичный path. Изображения
канонизируются существующим валидатором без метаданных. PDF проверяется по
размеру/заголовку/концевому маркеру; это не антивирусная сертификация. Согласующий
видит только статические финансовые поля и файлы snapshot своего назначения,
не банковские остатки, чужие финансовые документы или HR-версии. Предыдущее
назначение не даёт доступ к будущим файлам исправленной заявки.

Все изменения заявки охраняются плановым периодом; изменение даты проверяет
старый и новый месяцы в порядке возрастания. Блокировки request→approval/payable
→account→period, включая generic inbox dispatch, предотвращают обратный порядок
cancel/review. Новый платёж не переписывает сумму источника. Операции, аудит,
уведомления в одной локальной транзакции. Сохранённый файл очищается при ошибке
метаданных/аудита; crash между storage и SQL остаётся эксплуатационной задачей
сверки orphan-файлов, не распределённой транзакцией.

## Внедрение

Миграция0051 аддитивна, nullable ссылки сохраняют историю. POST старого direct
payment без payment_request_id теперь409 approval_required: намеренное закрытие
обхода. Клиент должен создать/согласовать заявку и загрузить proof. Доступ к
реестру finance.payable.read OR finance.payment.manage, записи/исполнение manage;
новые автоматические назначения ролей не создаются.

Рабочие миграции/deploy не выполнялись. Реальную конкуренцию проверяют на
PostgreSQL; SQLite не подтверждает row locks. Финансовое/налоговое закрытие,
FX и полное выполнение ТЗ этим этапом не заявляются.
