# ADR-0001: микросервисная цель и переход существующего backend

Дата: 31.10.2026.
Статус: заменён ADR-0002 по последующему явному решению пользователя.
Текст ниже сохраняет историю прежней политики; он больше не управляет текущей разработкой.
Прежний статус цели: принято явным указанием пользователя.
Статус границ сервисов, плана миграции и внедрения: предложений/утверждения пока нет.

## Контекст

Пункты ТЗ около строк 531 и 633 рекомендуют стартовый/модульный монолит.
Фактический проект использует Django backend с общими ORM-моделями, одной схемой
persistence и локальными транзакциями для склада/финансов/согласований.
В новой инструкции пользователь явно потребовал микросервисы с самого начала,
с владением схемами, API, инвариантами и запретом доступа к чужой БД.
Новая политика заменяет прежнюю рекомендацию для дальнейшего сервисного развития,
но не изменяет задним числом архитектуру уже написанного кода.

## Решение

Принять микросервисы как целевую политику. BE-01 координирует владельцев данных,
OpenAPI и версии событий до межсервисной реализации. Новые сервисы должны быть
независимо собираемыми/тестируемыми/развёртываемыми и не обращаться к чужой БД.
Использовать outbox/inbox, идемпотентность, retries/DLQ там, где нужны надёжные
события; распределённые транзакции — только по отдельному утверждению.

Текущая задача создаёт инструкции агентов. Она не разрешает автоматический
вынос текущих модулей, перенос данных, изменение действующих денежных/складских
инвариантов или развёртывание. Реализацию миграции оформить отдельной задачей.
Не продолжать расширение общей БД под названием «новый микросервис» молча.

## Неутверждённые решения для следующего архитектурного задания

BE-01 должен представить пользователю варианты и план:

- Точные bounded contexts, сервис-владельцы identity/approval/HR/склада/финансов
  и их OpenAPI/event-контракты. Перечень модулей ТЗ сам по себе не есть список сервисов.
- Владение сущностями и идентификаторами, авторизация между сервисами, private
  media и аудит без межсервисных FK/join или общей записи в таблицы.
- Как сохранить целостность приёмки, перемещений, списаний, сверок и платежей
  при разрыве текущих локальных транзакций; идемпотентность и компенсации.
- Выбор транспорта событий по требованиям доставки/эксплуатации, outbox/inbox,
  retry/dead-letter и наблюдаемость без заранее навязанного брокера.
- Этапы переноса, совместимость API, сохранение документов/фото/истории,
  backup/restore, rollback и критерии приёмки. Никаких destructive операций
  или production deploy без отдельного разрешения.

## Рассмотренные альтернативы

- Продолжать монолит как целевую политику: не соответствует новому указанию.
- Немедленно переписать все модули: нет утверждённых границ, контрактов и плана
  сохранения данных; выходит за scope настройки агентов.
- Зафиксировать цель и отделить от её миграционной реализации: выбранный вариант.

Этот ADR не утверждает конкретные сервисы, финансовые правила, брокер или
распределённые транзакции. Такие решения требуют отдельных ADR/уточнений.
