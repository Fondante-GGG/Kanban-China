# ADR-0005: отдельные корректировки неоплаченного долга по возврату

Статус: ограничение первого этапа подтверждено пользователем; технический
контракт согласован TL-01/BE-01/FE-01. Модульный монолит, ADR-0002.

## Основания и согласованный объём

ТЗ Б7.3 требует точных денежных сумм и отдельных документов исправления,
Г.6 — подтверждения финансовой корректировки и защиты закрытого периода.
Пользователь выбрал первый вариант: бухгалтер выбирает неоплаченный долг и
вводит подтверждённую сумму в той же валюте, не превышающую остаток долга.
Возврат денег и FX в этот этап не входят. Открытые правила ADR-0004 не
считаются утверждёнными целиком этим выбором.

Сумма документа не вычисляется из складской средней стоимости, закупочной
цены или количества. Бухгалтер задаёт сумму, валюту, дату проведения,
номер подтверждающего документа и обоснование. Для подтверждения используется
существующее право `finance.payable.manage`; отдельный новый маршрут
согласования и пороги сумм не вводятся. Просмотр — `finance.payable.read`.

## Границы и инварианты

- Источник — проведённый складской возврат с финансовой записью рассмотрения.
- Выбирается один открытый/частично оплаченный долг того же поставщика и
  того же исходного заказа. Валюта документа строго совпадает с валютой долга.
- Сумма — положительный decimal, максимум два знака, без скрытого округления;
  не больше актуального непогашенного остатка, проверяемого под блокировкой.
- Подтверждение атомарно создаёт отдельный неизменяемый документ и аудит,
  уменьшает только `outstanding_amount`. Исходная сумма долга, сверка,
  приёмка, заказ, платёжные записи и банковский/кассовый остаток не меняются.
- При нулевом долге устанавливается `settled_by_adjustment`, а не `paid`.
  При положительном остатке сохраняется прежний `open/partially_paid`.
  Последующая оплата остатка также сохраняет `settled_by_adjustment` при
  достижении нуля, если часть долга закрыта корректировками. Чистая оплата без
  корректировок по-прежнему приводит к `paid`.
- Дата нового документа должна относиться к открытому финансовому периоду.
  Исходный закрытый период не открывается и не переписывается.
- UUID `request_id` глобально уникален: точный повтор возвращает ранее
  проведённый документ, иное содержимое с тем же UUID отклоняется.
- Допускаются отдельные дополнительные документы по тому же возврату.
  Полная сумма требования не определена, поэтому финансовое рассмотрение
  остаётся `pending`. Наличие документа не означает завершение всех расчётов,
  принятие претензии поставщиком или получение денег. API закрытия рассмотрения нет.

Это финансовый регистр корректировок кредиторского долга, не полный главбуховский
журнал с корреспонденцией счетов. Налоги, курсовые разницы, оплаченная часть,
переплата/аванс и требование возврата денег остаются отдельными решениями.

## Техническое решение

Используются существующие Django ORM, локальная транзакция и decimal вместо
нового финансового сервиса, брокера или расчёта через float. Это сохраняет
атомарность изменения долга и аудита в текущем монолите.

Блокировки: финансовое рассмотрение → выбранный долг → финансовый период.
Платежи уже блокируют тот же долг, поэтому конкурирующие списания его остатка
сериализуются. Для периода создаётся/блокируется строка; будущая операция
закрытия периода обязана использовать такую же блокировку. Полноценного
API закрытия периода сейчас нет; ручной SQL обходит прикладные гарантии.

DB constraints защищают положительность и баланс документа. Проверка баланса
использует `ROUND(after + amount, 2)`: SQLite хранит числа не как PostgreSQL
NUMERIC, и прямое сравнение 0.30 = 0.20 + 0.10 там ложно. Прикладной расчёт
всегда выполняется точным Decimal без округления входа. На PostgreSQL NUMERIC
с двумя знаками эта проверка сохраняет точное денежное равенство.
Защита от ORM update/delete использует существующий AppendOnlyManager.

## Внедрение и ограничения

Миграция `0049_supplier_return_corrections` добавляет таблицу и расширяет
статус долга до 24 символов. Новые ответы API могут содержать статус
`settled_by_adjustment`; потребители с закрытым enum должны его поддержать.
Нет пересчёта старых данных и новых разрешений. Рабочая миграция не запускается.

Обратная миграция после проведения документов уничтожила бы их историю и
сузила статус долга; такой rollback не является безопасным способом отмены
денежной операции. Нужна отдельная согласованная корректировка/план сохранения
данных, а не удаление документа или возврат старого статуса вручную.

Реальные гонки требуют PostgreSQL; SQLite-тесты не подтверждают работу row locks.
