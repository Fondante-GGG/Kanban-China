# Финансовая корректировка возврата: UX handoff

Дата: 31.10.2026. Владелец UX-01. Основания: ТЗ Г.6, Б7.3;
ADR-0002/0004 и явный ответ пользователя: бухгалтер выбирает неоплаченный долг,
вводит подтверждённую сумму в валюте долга, превышение остатка запрещено;
возврат денег и валютные операции — отдельные этапы.

## Принятая граница

В существующей `SupplierReturnFinanceQueue` добавляется отдельный
подтверждённый корректирующий документ. Он уменьшает остаток выбранного долга.
Исходные приёмка, заказ, сверка, складской возврат, проведённые платежи и банк
не редактируются. Складская оценка не подставляется как сумма корректировки.

Несколько append-only корректировок допустимы. Финансовый review остаётся
pending: общая сумма требования по возврату неизвестна, поэтому UI не содержит
«Закрыть возврат» или «Возмещение завершено». Каждый подтверждённый документ
имеет собственный итог. Нулевой долг после корректировки обозначается
«Погашен корректировкой», не «Оплачен». Эти технические состояния согласованы
TL-01/BE-01; UI не вводит дополнительный маршрут согласования.

## Контракт для FE-01

BE-01 опубликовал GET/POST
`/api/finance/supplier-returns/{review_id}/corrections`.
POST: `request_id` UUID, `payable_id` integer, `amount` decimal-string,
`currency`, `posting_date` YYYY-MM-DD, `document_no`, `reason`.
Успех 201, точный повтор 200; 409 при ином содержимом того же ключа,
закрытом периоде или недостаточном остатке. GET возвращает неизменяемую историю
и подходящие долги того же поставщика и заказа. Независимая пагинация:
`limit/offset` для истории и `payable_limit/payable_offset` для долгов
(default20/max100); `q` — поиск долгов по id/source_id. Response: `corrections`,
`correction_count`, `payables`, `payable_count`, `can_confirm`, review id/status
и параметры пагинации. Смена страницы долгов не меняет страницу истории.
DTO подтверждения: id/review_id/return_id/payable_id/request_id/amount/currency/
posting_date/document_no/reason/outstanding_before/outstanding_after/
confirmed_by_name/confirmed_at. Точные имена сверить с финальным API-документом,
не обращаться к старому общему списку первых 200 долгов.

Чтение — `finance.payable.read`; подтверждение — `finance.payable.manage`.
Права подтверждения получать из явного серверного признака и текущих прав,
не из имени роли. Backend всегда повторно валидирует права/связи/остаток/период.

## Размещение и маршрут

Сохраняются очередь, переход из уведомления по return_id, исходные сведения
и защищённые фото. В каждой карточке новый блок «Корректировки задолженности»:
краткая история и кнопка «Уменьшить задолженность» при наличии права.
Кнопка раскрывает inline-форму, modal не нужен. Одновременно редактируется
одна карточка; при переключении контекста инвалидировать задержанные запросы.

Порядок: поставщик/заказ/приёмка/возврат только для чтения → выбор долга →
сумма → дата проведения → номер документа → основание → «Проверить» →
summary → явное «Подтвердить уменьшение долга». Первая отправка формы не
проводит деньги. Пользователь может вернуться к редактированию. Перед final
POST summary перечисляет возврат, долг, валюту, остаток до, уменьшение,
ожидаемый остаток после, дату и номер документа. Текст: «Будет создан отдельный
корректирующий документ. Остаток задолженности уменьшится. Проведённые платежи
и банковские остатки сохранятся. Подтверждённый документ нельзя редактировать».

Сумма вводится как строка с `inputMode=decimal`; нормализация десятичной запятой
допустима, но отправлять точную десятичную строку, не результат float-арифметики.
Не принимать экспоненту, NaN, Infinity, ноль, отрицательные значения или более
двух десятичных знаков. UI показывает валюту рядом с input и выбранным долгом.
Валюта readonly; ни свободного валютного выбора, ни FX-переключателя.
Итог preview считать точной десятичной арифметикой либо показывать серверный
расчёт; authoritative before/after после подтверждения приходит от сервера.

Долг в select: номер сверки/идентификатор, исходная сумма, текущий остаток и
валюта. Не выбирать первый автоматически и не подставлять сумму остатка или
складской оценки. Дата — date input, осмысленный label. Номер/основание —
связанные label и явные ограничения из API; причина обязательна по контракту.
Дата закрытого месяца блокируется сервером, UI не предлагает открыть период.

## История и результат

История по каждому документу: номер, дата проведения, выбранный долг/сверка,
валюта, подтверждённая сумма, остаток до/после, автор и время подтверждения,
основание. Неизменяемые факты до/после не заменять текущим остатком долга.
На мобильном — article + dl, не широкая обязательная таблица. Суммы не скрывать
через truncation; длинный номер/основание переносится.

После 201/200 убрать форму и показать подтверждение (`role=status`), вернуть
фокус на заголовок созданного документа/блока истории, перечитать долги и историю.
Review pending остаётся видимым с пояснением: «Корректировки по документам
подтверждаются отдельно. Полное финансовое урегулирование возврата не завершено».
Доступ к подтверждённым документам сохраняется при точном lookup из уведомления.

## Состояния и ошибки

- Loading history/catalog: отдельный `aria-busy`, не очищать исходный документ;
  отключить final confirm пока данные не готовы.
- Empty payables: «Нет подходящих непогашенных долгов по этому заказу»;
  не предлагать другой заказ, FX, отрицательный долг или возврат денег.
- Empty history: «Корректирующих документов пока нет».
- 400: понятное локализованное field error, `aria-invalid`, `aria-describedby`;
  сохранить введённое и фокус на первой ошибке.
- 401/403: убрать форму и финансовые подробности при отзыве доступа,
  инвалидировать запросы, показать localized forbidden. Не оставлять фото Blob.
- 409 остаток изменился: перечитать выбранный долг/историю, сохранить input,
  сбросить preview и требовать нового явного подтверждения актуального summary.
- 409 закрытый период: сохранённые данные, error у даты; нельзя обойти заменой
  статуса review. Исправление — новая допустимая дата и проверка формы.
- Network/5xx after POST: результат неизвестен; не утверждать «не проведено».
  Сохранить request_id и точный payload для безопасного retry, перечитать историю.
  Не создавать новый UUID на повтор той же операции. После изменения данных
  новая операция получает новый ключ; до разрешения неизвестного результата
  UI не должен молча отправлять изменённый payload как ещё одну корректировку.
- Повторный клик/Enter: одна операция, busy guard; не только disabled styling.
- Stale request при смене карточки/локали/страницы/unmount не изменяет текущую
  форму и результат. Отмена ожидания не означает отмену серверной корректировки.

## Визуальные и accessibility-правила

Использовать существующие slate tokens SupplierReturnFinanceQueue:
white/slate-950, dark slate-900/slate-100, borders slate-300/dark slate-600,
secondary slate-600/dark slate-300. Ошибки rose-800/dark rose-200,
предупреждение amber-900/dark amber-200. Status всегда сопровождается текстом.
Основное подтверждение blue-700/white с заметным focus outline; не вводить
новую тему/цветовую систему и не менять соседний expense UI.

Карточка p4, секции gap4, поля gap3; заголовок h3/h4 по текущей иерархии.
Форма одна колонка на 360px, две с sm при достаточном месте; основание и summary
на полную ширину. Input/select min-width:0, width100%, кнопки min-height44px,
toolbar wrap. Очередь может остаться lg двухколоночной, расширенная форма/история
не должна переполнять карточку. Не опираться на hover-only пояснения.

Keyboard: обычные native controls, логичный tab order, labels не placeholder,
fieldset/legend для preview, явные type=button вне submit. Раскрытие использует
aria-expanded/aria-controls; фокус перемещается к форме и возвращается к
инициирующей кнопке при отмене. Summary не trap: это inline секция.
Screen-reader status — live polite, ошибки — alert без дублирования при рендере.
Цель WCAG2.1AA: текст >=4.5:1, focus/значимые границы >=3:1; фактическую
инструментальную проверку делает FE/TL, этим handoff она не заявлена.

## Локализация

Все новые labels/ошибки/status/help/confirm/read-only строки — RU/KY/zh-Hans/
zh-Hant, без fallback к русскому для доступного локализованного текста.
Не переводить номера, валютные коды, введённое основание/номер документа.
Даты и представление сумм форматировать locale, но payload сохраняет ISO/decimal.
Пример базовых названий:

| RU | KY | zh-Hans | zh-Hant |
| --- | --- | --- | --- |
| Корректировки задолженности | Карызды оңдоо документтери | 应付款调整 | 應付款調整 |
| Уменьшить задолженность | Карызды азайтуу | 减少应付款 | 減少應付款 |
| Выберите задолженность | Карызды тандаңыз | 选择应付款 | 選擇應付款 |
| Сумма уменьшения | Азайтуу суммасы | 调减金额 | 調減金額 |
| Дата проведения | Өткөрүү күнү | 过账日期 | 過帳日期 |
| Номер документа | Документтин номери | 单据编号 | 單據編號 |
| Основание | Негиз | 调整依据 | 調整依據 |
| Подтвердить уменьшение долга | Карызды азайтууну ырастоо | 确认减少应付款 | 確認減少應付款 |
| Погашен корректировкой | Оңдоо аркылуу жабылган | 已通过调整结清 | 已透過調整結清 |

FE дополняет все сопутствующие строки в четырёх локалях; не отправлять raw
backend error в UI. Редакционная/носительская проверка KY остаётся ограничением.

## Ожидаемые файлы и приёмка

Основные FE ownership-файлы: SupplierReturnFinanceQueue.tsx; новая
SupplierReturnCorrections.tsx при выделении сложной логики;
`lib/supplier-return-corrections-i18n.ts`; `lib/api.ts`; `types/index.ts`.
FinanceView передаёт только нужные права/currentUser, если серверный GET не даёт
capabilities. Существующие ReturnPhotos и Navbar/page не менять без необходимости.
Контракт/API/миграции остаются BE-01; handoff — UX-01.

Проверить вручную/автоматически: read-only роль не видит write action; правильный
долг поставщика/заказа; пустой каталог; ручная сумма не подставляется из склада;
полная confirmation; сумма меньше/равна/больше остатка; closed date; stale debt
409; права отозваны; двойной клик; неизвестный POST и повтор с тем же ключом;
неизменная банковская сумма; история нескольких документов при review pending;
точный lookup из уведомления; переключения/запоздалые ответы; четыре локали,
360/1440, обе темы, keyboard, axe и отсутствие горизонтального переполнения.
Browser mock отделить от Django-интеграции и PostgreSQL concurrency-тестов.

Документ подготовлен по инспекции текущего UI и ТЗ, без production-кода и без
заявления браузерных/контрастных проверок. Финальные response DTO сверить с BE.
