# Межскладские перемещения: handoff

Дата: 31.10.2026. Основания: Б7.7 и Г.7 объединённого ТЗ,
`docs/design/warehouse.md`, текущий `WarehouseView.tsx` и согласуемый контракт
`transfer_backend`. Владелец этого файла — Designer; production frontend —
Frontend Developer. Точная форма DTO и методов закрепляется Backend в
`docs/api/transfers.md`; frontend не обходит отсутствующие разрешения.

## Назначение и маршрут

Отправитель создаёт перемещение между двумя разными складами и передаёт его
на согласование. Независимый согласующий утверждает, возвращает в черновик
с причиной либо отклоняет. После утверждения отправитель отдельно подтверждает
отправку: физический остаток источника уменьшается, количество появляется
«В пути». Получатель отдельно подтверждает получение: только тогда увеличивается
физический остаток назначения, а количество в пути обнуляется.

Статусы: «Черновик» → «На согласовании» → «Согласовано» → «В пути» → «Получено».
Отдельные конечные состояния: «Отклонено», «Отменено». Возврат на доработку
возвращает документ в черновик, а причина сохраняется в истории. Отмена после
отправки недоступна. Согласование само по себе не изменяет остатки.

Точный набор действий всегда берётся из серверного `allowed_actions`:
`edit`, `submit`, `review`, `dispatch`, `receive`, `cancel`. Не заменять его
проверкой одной общей роли. Отсутствие разрешения не обходить вызовом старого
`/post`: этот endpoint больше не является прямым способом перемещения.

## Размещение и состав компонентов

Добавить «Перемещения» к обычным кнопкам представлений WMS с `aria-pressed`,
при складском праве чтения перемещений. Сохраняется общий выбранный склад.
Реализация отдельным `TransferView` внутри `WarehouseView` предпочтительна:
список, форма, детали и собственная загрузка не раздувают уже существующий
компонент. Название компонента допустимо согласовать с Frontend.

Список: номер; источник → назначение; статус; дата; количество в пути;
явная кнопка «Открыть». Таблица на desktop, карточки `article + dl` на mobile.
Документ доступен, если пользователь имеет серверный доступ хотя бы к одной
его стороне. Просмотр входящего документа не открывает остатки чужого склада.
Не превращать имя склада-контрагента в ссылку к его остаткам.

Под заголовком представления: «Обновить», «Новое перемещение» по правам и
доступным источникам. Фильтр статуса и пагинация — только по поддерживаемым
сервером параметрам. Выбранный склад фильтрует и исходящие, и входящие документы.
Смена фильтра сбрасывает страницу и не оставляет детали другого контекста.

Строка движения `stock_transfer` показывает номер перемещения и кнопку
«Открыть документ» при праве чтения. Открытие использует точный lookup по ID,
а не поиск в первой странице списка. Допустим `initialTransferId` или callback
в `TransferView`: при переходе фокус на заголовок деталей, при закрытии — на
исходную кнопку, если она ещё существует, иначе на заголовок представления.

## Форма создания и редактирования

Inline-форма с постоянными labels. Поля: уникальный номер; склад-источник;
склад назначения; строки SKU/количество/ячейка источника/ячейка назначения/
партия. Источник выбирается из назначенных пользователю складов. Назначение
выбирается из разрешённого справочника имён и ячеек, без выдачи его остатков.
Одинаковые source/destination запрещены; не предоставлять произвольный ввод ID.
При смене стороны сбрасывать зависимые ячейки и выбранную партию. Не сохранять
невидимое старое значение после смены SKU или склада.

Строки — `fieldset/legend` с номером, «Добавить строку» и «Удалить строку N»;
минимум одна. SKU выбирается из доступного справочника активных товаров.
Рядом показывается физический доступный остаток только источника и выбранной
ячейки. Он справочный: финальную доступность сервер проверяет при отправке.
Количество — положительное целое по контракту; пустое значение не превращать
в ноль. `null` ячейка отображается как «Без ячейки».

Партия выбирается из партий выбранного SKU/ячейки источника. Показывать её
номер, срок годности и физическое количество; срок берётся из выбранной партии,
не редактируется как новая дата. Если требуется непартийный остаток, явно
различить «Без партии» от конкретной партии; не предлагать его для обхода
партийного учёта. Себестоимость не вводится и не подставляется нулём.

Ограничение текущего контракта: один SKU в документе встречается один раз,
то есть одна партия одного SKU на документ. Для двух партий одного SKU нужны
отдельные документы. Показать это коротким пояснением у строк и исключить
повторный выбор SKU. Приёмка выполняется целиком в отправленном количестве;
частичное получение и маршрут расхождений в этот этап не входят.

«Сохранить черновик» и «Передать на согласование» — разные действия. Не
отправлять новый документ автоматически после сохранения. Редактирование
доступно только если сервер вернул `edit`. При ошибке серверной валидации
сохранять ввод; при успехе закрывать форму и открывать сохранённый документ.
Отмена редактирования — явная кнопка, фоновое обновление не затирает текст.
В существующем черновике номер и пара складов неизменяемы: показать их
как текст, редактируются только строки и комментарий. Для другого маршрута
создаётся новый документ. Отклонённый документ — конечное состояние;
возвращённый на доработку становится редактируемым черновиком.

## Детали и подтверждения

Заголовок с номером, статусом, источник → назначение. Ниже последовательный
семантический список этапов: создание, согласование, отправка, получение.
Для выполненного этапа — actor и время из сервера; неизвестные legacy-события
не подписывать как достоверно выполненное независимое согласование.

Строки деталей: SKU/название, source/destination ячейка, партия/срок, количество,
количество в пути. Показывать явную подпись «В пути — не физический остаток
склада назначения». При `in_transit` отправленное количество ещё не числится
полученным; при `received` отображается нулевое количество в пути.
Стоимость/цена показываются только при наличии соответствующего поля DTO,
без вывода вычисляемого итога из скрытых значений.

Согласование: «Согласовать», «Вернуть на доработку», «Отклонить».
Для возврата/отклонения обязательна причина; сохранить её в видимой истории
по серверному DTO. Не подсказывать пользователю сменить аккаунт для обхода
запрета утверждения собственного документа.

«Подтвердить отправку»: пояснение «Количество спишется со склада-источника
и будет учитываться в пути. Остаток получателя пока не изменится».
«Подтвердить получение»: показать отправленные количества и пояснение
«Подтверждается получение всего документа; остаток склада назначения
увеличится». До вызова необратимого действия — короткое явное подтверждение
inline с «Подтвердить»/«Назад» либо доступный существующий dialog.
Если фактическое получение не совпало с отправленным, не подтверждать
получение: частичная приёмка и разбор расхождений ещё не поддерживаются,
требуется отдельное решение ответственного. Это ограничение показать
непосредственно рядом с подтверждением, а не только в документации.
Отмена документа также требует явного подтверждения; после отправки её нет.

## Состояния, ошибки и доступность

Начальная загрузка — локализованный `role=status` и `aria-busy`; пустое
состояние появляется после ответа. Различать отсутствие документов, отсутствие
назначенного склада-источника и отсутствие права. Входящие документы могут
быть доступны пользователю без права создания: не скрывать весь список из-за
отсутствия доступного источника формы.

401/403: очистить недоступные детали, формы и действия, обновить каталог.
409: обновить точный документ и `allowed_actions`, объяснить конфликт без
повторного автоматического проведения. Если обновление не удалось, не
оставлять прежние кнопки записи как актуальные. Сеть/500: сохранить введённые
поля, показать retry. Не локализовать бизнес-ошибки по английскому `message`:
использовать стабильные коды и общий fallback.

При сохранении отключить повторное действие и смену контекста. Старый ответ
загрузки не должен переписывать новый склад/документ. Повтор отправки/получения
не добавляет локальный дубль; после успеха обновить точный документ, список и
каталог источника. Не оставлять старую кнопку действия после успешного ответа.

Все inputs имеют связанные label, required и errors через `aria-invalid`/
`aria-describedby`. Ошибки — `role=alert`, успех — `role=status`.
Динамические строки не перемещают фокус без причины; после удаления фокус
переходит на ближайшую строку/«Добавить». Таблицы имеют caption и `scope=col`.
Все действия — нативные button, keyboard reachable, hit-target ≥44px.

## Layout и визуальные tokens

Сохранить оболочку WMS `max-w-7xl`, 16px padding mobile/24px desktop;
вертикальные интервалы 16–24px. Заголовок раздела 24px bold, секции 18px
semibold, основной текст 14–16px. Формы: одна колонка <640px, две ≥640px;
длинные SKU/причины — полная ширина. Desktop таблица прокручивается только
в своём контейнере; при 360px карточки не выходят за viewport. Применять
`min-w-0`/`break-words` к длинным номерам, именам, партиям и комментариям.

Повторно использовать tokens WMS: `bg-white dark:bg-slate-900`,
`text-slate-950 dark:text-slate-100`, secondary
`text-slate-600 dark:text-slate-300`, border
`border-slate-300 dark:border-slate-600`. Primary `bg-blue-700 text-white`,
hover `bg-blue-800`; не наследовать конфликтующий светлый hover neutral button.
Ошибка `text-rose-800 dark:text-rose-200`, предупреждение
`text-amber-900 dark:text-amber-200`. Текст ≥4.5:1, focus/границы ≥3:1.
Статус передаётся текстом, не только цветом. Видимый focus-ring 2px с offset.

## Локализация и ожидаемые файлы

Все labels, статусы, действия, подтверждения, ошибки, пустые состояния,
aria-label и пояснения должны иметь независимые строки RU/KY/zh-Hans/zh-Hant.
Использовать типизированный `transfer-i18n.ts`, даты/числа через Intl выбранной
локали. Имена RU/KY/ZH из DTO — с понятным fallback; не переводить коды SKU.

Ожидаемые изменения Frontend: новый `TransferView.tsx`, новый
`lib/transfer-i18n.ts`, DTO в `types/index.ts`, методы в `lib/api.ts`,
вкладка/открытие источника в `WarehouseView.tsx`; Navbar не требует новой
верхнеуровневой вкладки. Глобальные tokens и зависимости не менять без причины.
Backend-владение, migrations и API остаются у Backend Developer.

## Приёмка

1. Отправитель создаёт черновик на другой склад, редактирует, передаёт на
   согласование; собственное независимое утверждение не предлагается.
2. Другой согласующий утверждает/возвращает/отклоняет, причина видна; до
   отправки физические остатки не меняются.
3. Отправитель подтверждает отправку: источник уменьшается, назначение ещё
   не увеличивается, документ и строки показывают количество в пути.
4. Получатель видит входящий документ и подтверждает полное получение;
   повтор не удваивает остатки, статус и действия сохраняются после reload.
5. Ячейки и партия не теряются; источник партии и срок читаемы. Смена склада,
   SKU и ячейки сбрасывает зависимые значения; повторный SKU не принимается.
6. Чужие остатки/цены недоступны; справочник назначения не означает доступ
   к его inventory. Открытие перемещения из движения работает по точному ID.
7. Проверены 403, 409, network fail, повторные клики, отмена до отправки,
   пустые данные, обе темы, четыре языка, keyboard-only и ширина 360px.
8. Исполнитель перечисляет реально выполненные проверки отдельно от
   непроведённых browser/axe/контраст/скринридер; ревью всего ТЗ не заявляется.
