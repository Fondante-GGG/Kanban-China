# Заявки на оплату поставщикам: UX handoff

Дата:31.10.2026. UX-01. Основание: ТЗ Г.6 (платёж только после согласования
заявки), Б7.3/573/675, ADR-0002; технический контракт BE-01/TL-01 текущего этапа.
Изучены FinanceView, ApprovalsView, существующие financial period/correction
экраны. Это передача frontend, не заявление завершённости реализации.

## Граница этапа

Заявка создаётся по одному непогашенному долгу поставщика. Валюта долга,
заявки и выбранного активного счёта должна совпадать. Частичная оплата долга
возможна несколькими заявками; одна утверждённая заявка допускает один платёж
ровно на согласованную сумму, с согласованного счёта и на согласованную дату.
Согласование не означает оплату и не резервирует банковский остаток или долг.
При регистрации платежа сервер повторно проверяет актуальный долг, доступность
денег, валюту и открытый финансовый месяц. Не обещать платёж до успешного API.

Применяется настроенный последовательный маршрут finance_payment_request.
Если его нет или в нём нет действующего независимого согласующего, отправка
невозможна; интерфейс объясняет необходимость настройки маршрута и не выбирает
директора автоматически. Порогов сумм, параллельного/all согласования, новых
делегирований и автоматического назначения полномочий данный этап не вводит.
Маршрут и финансовый снимок сохраняются при отправке; пользователь не утверждает
собственную заявку даже при роли директора. Изменения возвращённой заявки
требуют новой отправки и новой записи согласования.

## Контракт BE-01

Точные DTO сверить с финальным docs/api и OpenAPI, не обходить серверные flags.

- GET /api/finance/payment-requests: limit(default20/max100),offset,q,status,id exact;
  items,count,limit,offset,can_create.
- POST collection: request_id UUID,request_no<=64,payable_id int,account_id int,
  amount decimal-string positive с максимум14+2 цифрами,currency uppercase3,
  planned_payment_date ISO,purpose<=4000. 201создание,200точный повтор.
- GET /catalog: limit,offset,q,payable_id exact,account_id exact; payables (id,supplier_id,supplier_name,source_id,
  amount,outstanding_amount,currency,status),payable_count,accounts(id,name,currency),
  flow_configured. Каталог для финансового пользователя, не для произвольного
  согласующего. Текущий выбор из details сохранять и при смене страницы каталога.
- GET/PATCH /{id}: detail/history; менять только draft/returned. request_id и
  request_no неизменяемы. После edit старый approval не является разрешением на оплату.
- POST /{id}/submit {}:202. POST /{id}/cancel {comment}:200.
- Detail: id,request_id,request_no,payable_id,supplier_id,supplier_name,account_id,
  account_name,amount,currency,planned_payment_date,purpose,status,created_by_id,
  created_by_name,created_at,approval_id,approval_status,assigned_to_id,
  assigned_to_name,current_node,payment_id,payable_outstanding_amount,allowed_actions,proofs,history.
- allowed_actions: edit/submit/cancel/pay/upload_proof/delete_proof. Отсутствие действия означает отсутствие
  права/допустимого перехода, а не предложение проверить роль на frontend.
- Центральный approval detail содержит финансовый snapshot и сохранённый
  route(order,assignee_id), без банковских остатков и посторонних HR versions.
- POST /finance/payables/{id}/payments теперь требует payment_request_id,
  account_id,amount,payment_date,transaction_no,proof_id (обязателен).
  account/amount/date ровно из утверждённого снимка;201новый платёж,200точный повтор,
  409конфликт. Старый прямой платёж без заявки не должен обходить согласование.
- Месяц заявки определяется planned_payment_date: draft/edit/submit/review/cancel
  закрытого месяца блокируются. Оплата проверяет ту же согласованную дату.

## Экран финансов

В существующем FinanceView самостоятельный section «Заявки на оплату» перед
длинными списками расходов. Не заменять existing расходы/возмещения, периоды и
возвраты. У заголовка краткий текст: «Сначала согласуйте заявку. Регистрация
платежа доступна после утверждения; согласование не резервирует деньги».

Сверху toolbar: статус, поиск по поддерживаемому API значению, обновить,
«Новая заявка» при can_create. Поиск/страницы сбрасывают устаревшие details;
точный id lookup открывает нужный документ вне первой страницы списка.
Список карточками или адаптивной таблицей с минимумом колонок: номер, поставщик,
сумма+валюта, плановая дата, локализованный статус, «Открыть». На360px карточки,
на desktop можно компактную таблицу с локальным scroll без overflow страницы.
Не показывать внутренний raw finance_payment_request, UUID или source_type
как заголовок/название в пользовательском маршруте.

Inline форма новой/возвращённой заявки: номер (новая только), долг, счёт,
сумма, плановая дата, назначение. Долг отображается как поставщик+номер/id сверки,
исходная сумма и доступный остаток; выбранный счёт — имя и валюта. Смена долга
сбрасывает несовместимый счёт и просит подтвердить ручную сумму, без молчаливого
пересчёта. Сумма — строка с inputMode decimal; точное сравнение и форматирование
через decimal/string/BigInt cents, без Number/toFixed над денежным значением.
Нельзя автоматически подставлять весь остаток как уже подтверждённую сумму.
Плановая дата ISO в payload, дата UI в locale. Ввод суммы допускает локальную
запятую с явной нормализацией, если backend получает каноническую точку.

«Сохранить черновик» не отправляет на согласование. После сохранения detail
показывает итог: поставщик, долг, счёт, сумма/валюта, дата, назначение, автор.
«Отправить на согласование» требует отдельного summary с этими значениями и
предупреждением об их фиксации и отсутствии движения/резерва денег.
Если flow_configured=false, сохранение черновика возможно, submit недоступен
с читаемой причиной. Сервер остаётся авторитетным при изменившейся конфигурации.

Detail показывает текущего согласующего/этап, всю history и предыдущие решения
с причиной. «Вернуть на исправление» требует причины; applicant видит её рядом
с формой. Возвращённая заявка редактируется и отправляется заново; rejected
терминален. Cancel до оплаченного состояния — отдельное подтверждение с причиной,
оно отзывает pending approval; не скрывать факт отмены из истории.
Approved финансовые поля не редактируются: для иной суммы/счёта/даты — отмена
и новая заявка по правилам backend, не PATCH утверждённого снимка.

## Центральные согласования

В ApprovalsView заменить только представление payment business type понятной
меткой «Заявка на оплату»; сохранять прежние HR/other сценарии. В списке полезны
номер, поставщик, сумма+валюта и текущий статус, если DTO это предоставляет.
В details перед кнопками обязательный readonly financial snapshot: номер,
поставщик/долг, счёт, сумма+валюта, плановая дата, назначение, инициатор,
этап/сохранённый маршрут и решения. Если assignee name отсутствует, id — допустимый
вторичный идентификатор, но не выдумывать имя по текущему live каталогу.
Не запрашивать общий финансовый каталог из approval-only роли.

Действия решает backend allowed_actions/can_act. При отсутствии контрактного
capability FE запрашивает его у BE, а не выводит право из scope/role.
«Согласовать этап» не всегда означает итоговое утверждение заявки; после ответа
pending показывать следующий этап, после approved — «Заявка утверждена».
Возврат/отказ требуют комментарий; submit validation переводит фокус к полю.
Director не получает UI/selfapprove обход; результат403 очищает действия и
обновляет авторитетное состояние. История решений не смешивается с посторонними
кадровыми версиями совпадающего business_id.

## Регистрация платежа

Только allowed_actions pay открывает inline форму. Одобренные счёт, сумма,
валюта, долг и дата — readonly. Ручные поля: номер банковской/кассовой операции
и выбор фактически загруженного подтверждающего документа этой заявки.
Перед POST summary: «Зарегистрировать платёж», счёт/долг/сумма/дата/номер,
«Остаток счёта и задолженность уменьшатся. Заявка будет отмечена оплаченной».
Двойной клик заблокирован. Успех показывает payment_id/номер операции и paid,
не предлагает повторно оплатить; детали исторического платежа читаемы.

### Фактические подтверждающие документы

TL/BE включили реальное приватное хранение доказательств в текущий этап.
Финальный контракт: POST /finance/payment-requests/{id}/proofs multipart file;
DELETE /{id}/proofs/{proof_id} — логическое исключение; GET
/{id}/proofs/{proof_id}/download — авторизованные байты. ProofDTO:
{id,file_name,content_type,size,download_url}. Нет пользовательского proof_file
или пути файловой системы. Подробности — /tmp/yrys-payment-be/docs/api/payment-requests.md.

Отдельный блок «Подтверждающие документы»: input typefile с acceptPDF/JPEG/PNG/WebP,
имя локального выбранного файла и отдельная кнопка «Загрузить документ».
Выбор файла не считается загрузкой и не допускает выполнение платежа.
После201 файл появляется в серверном списке; локальный input очищается только
после успеха. При отказе файл сохраняется для Retry, без повторного POSTexecute.
До5активных файлов; PDFдо15MiB, картинки до10MiB/20MP. Сервер валидирует реальное
содержимое. Пояснение ограничений возле input, ошибки локализованы по code.
Не обещать антивирусную проверку: PDFheader/endmarker — не malware certification.

Загрузка/исключение допустимы только draft/returned/approved и только по flags.
Вpending/rejected/cancelled/paid блок readonly, оплаченные доказательства
неизменяемы. На approved загрузка фактического банковского подтверждения не
меняет утверждённую сумму/счёт/дату. При удалении — подтверждение с именем
документа, исходная история не представляется физически стёртой.

Для выполнения платежа пользователь выбирает один активный серверный proof
с понятным именем; можно выбрать единственный файл явно в форме. До фактической
загрузки/выбора summary/execute недоступны с объяснением. Summary включает имя
подтверждения, POSTпередаёт только proof_id этой заявки, не URL/локальное имя.
Защищённое скачивание выполняется через authenticated fetch→Blob→download,
а не прямой publichref. При использовании превью загрузка lazy, abort+revoke
ObjectURL на закрытии/смене документа/403/unmount. Не вставлять PDF в inlineiframe
как будто безопасный открытый ресурс.404пропавшего файла не изображается успехом.
Не загружать доказательства для approval-only роли через финансовый каталог:
у неё финансовый snapshot, а расширение доступа к proofs требует отдельного
серверного контракта, текущий его не предоставляет.

## Состояния и безопасные повторы

- Loading: status/loading, aria-busy; закрыть финансовые mutation actions.
- Empty: осмысленный текст по фильтру, create только при capability.
- Missing flow/approver: отдельная локализованная409причина, без fallback.
- Validation: label+aria-invalid+error id и фокус к первому ошибочному полю.
-409period_closed: дату/период исправляют в допустимом черновике и повторно
  согласуют; нельзя молча менять approved date на текущую.
-409изменился долг/недостаток денег: reread фактов, не снимать утверждение
  ради обхода лимита и не показывать успешную оплату.
-403/401: очистить financial details/preview/draft capability, отменить/игнорировать
  запоздалые ответы по generation/session; фото/вложения не сохранять в браузерный storage.
- Create lost response: сохранить один UUID+тот же payload и повторять точную
  операцию. Не генерировать новый ключ на Retry. После неизвестного результата
  поля snapshot заблокированы до авторитетного ответа.
- Execute lost response: тот же payment_request_id и весь платёжный payload;
  не разрешать менять transaction_no, account,amount,date при Retry. Успешный
  replay200 — уже зарегистрированный платёж, не новый. Закрытие details/remount
  не должно превращать неизвестный результат в новый свободный POST.
- Смена фильтра/заявки/года/языка не допускает запоздалого воскрешения чужого
  снимка. Cleanup запросов и фокуса обязателен. Ограничения сохранения ключей
  при полном reload документировать; не писать финансовые данные/токены в
  localStorage/sessionStorage ради удобства без privacy-решения.

## Визуальная система и accessibility

Спокойные bordered sections как FinancePeriods/Corrections: padding16/24,
space12/16, heading20px semibold, body14px, muted slate600/dark300.
Форма одна колонка360, sm две, purpose/ошибки/summary на всю ширину. Grid children
min-w-0, input/select width100%, длинные номера и причины break-words. Кнопки
минимум44px, toolbar wrap. Историю не прятать в hover-only элемент.

Нейтральные buttons и primary получают отдельные hover/background классы;
не наследовать slate-hover в синей primary. Primaryblue700/white, focusblue600;
опасное отмена/reject rose, warningamber900/dark200. Контраст текста≥4.5:1,
значимых границ/focus≥3:1 — цель; проверяется FE/TL инструментально на итоговом
UI, этим handoff результаты проверки не заявлены.

Native labels не placeholder, disabled состояния не единственное объяснение
права, ошибки rolealert/status-live без дублирования; controls с typebutton
вне submit. Summary inline fieldset/legend с фокусом, return edit возвращает
фокус к форме; cancel возвращает к trigger. Если используются dialog,
применять существующий AccessibleDialog с Escape/focus trap/restore.
Disclosure aria-controls указывает существующий div и aria-expanded отражает
реальное состояние. Клавиатурная последовательность логична, color не единственный
носитель статуса. Банковский счёт/валюта не являются локализуемыми идентификаторами.
