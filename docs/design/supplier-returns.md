# Возврат поставщику: UX handoff

Дата: 31.10.2026. Владелец UX-01. Основания: Б7.7, Г.6, Г.7 и Г.13.9
объединённого ТЗ; существующие WarehouseView, TransferView, WriteoffView и их
handoff. Реализация — модульный монолит по ADR-0002.

## Границы и зависимости

Экран оформляет документальный возврат товара поставщику с прослеживаемостью
до проведённой приёмки. Утверждение и физическая отправка — разные действия.
Исходная приёмка остаётся историческим фактом. Финансовая служба получает
уведомление о проведённом возврате и отдельно подтверждает бухгалтерскую
корректировку по Г.6. Физический возврат не означает автоматически возврат денег,
уменьшение задолженности или завершение финансового учёта.

Контракт BE-01 из `docs/api/supplier-returns.md` принят TL-01 и FE-01.
Действия: edit/upload_photo/delete_photo/submit/cancel/review/post. Статусы:
draft/pending_approval/approved/posted/rejected/cancelled; review return → draft.
Складские права warehouse.return.read/manage/approve/post; стоимость —
warehouse.cost.read. Финансовый реестр — finance.payable.read.
Решения о зачёте в оплаченную сверку, возврате денег, валюте и закрытом периоде
относятся к финансовому контракту/ADR; UI не вычисляет их самостоятельно.

План: отдельное представление WMS → список и точный lookup → создание по
приёмке → независимое решение → подтверждение отправки → показ фактического
финансового состояния. Приёмка описана в конце документа.

## Компоненты и размещение

Добавить «Возвраты поставщикам» в существующий переключатель WMS, обычная
кнопка с `aria-pressed`, без неполного ARIA tablist. Общий склад сохраняется.
Новая верхнеуровневая навигация не нужна. Видимость и действия определяет
серверный каталог прав и `allowed_actions`, а не название должности.

Отдельные SupplierReturnView и supplier-return-i18n; WarehouseView содержит
только интеграцию и открытие первичного документа. Inventory: toolbar,
status filter, list/table, pager, draft form, line fieldsets, detail summary,
review reason, dispatch confirmation, finance status, history и при наличии
API защищённые фотографии. Не превращать WarehouseView в общий редактор.

Список: номер возврата; приёмка; поставщик; склад; складской статус; дата;
финансовое состояние, если API его предоставляет; явная кнопка «Открыть».
Desktop — table/caption/th scope=col. Mobile — article + dl, кнопка открытия.
Фильтры и пагинация только поддержанные API. Не искать документ только в первой
странице: движение возврата открывает его через точный серверный ID.
При ошибке lookup retry сохраняет исходный ID; смена контекста отменяет намерение.

## Создание и изменение

Показывать только разрешённые пользователю проведённые приёмки выбранного
склада. В варианте выбора: номер, дата, поставщик, связанный заказ при наличии.
Выбранная приёмка определяет поставщика и склад: read-only, без независимого
редактирования. После сохранения источник неизменяем; другой источник требует
нового документа. Номер и обязательная причина — по фактическому API.

Строка выбирается по receipt_item_id; рядом SKU/название, исходная ячейка,
партия, срок годности и принятое количество. Склад/поставщик/ячейка/партия
выводятся сервером из исходной приёмки и неизменяемы. Произвольные SKU/партии/
ячейки и выбор текущей другой ячейки не предлагаются. Смена источника сбрасывает
строки. Товар после перемещения из исходной ячейки может оказаться недоступен
для этого документа; не обходить отказ выбором любого остатка SKU.

У каждой строки: «Принято», «Уже возвращено», «Можно вернуть по приёмке» и
«Сейчас доступно» только при наличии этих отдельных значений в DTO. Это разные
ограничения. Не подменять отсутствующие данные нулём и не считать черновики
зарезервированным товаром. Количество — положительное целое по контракту исходной приёмки; дробный ввод
объяснить ошибкой, не округлять молча. DTO возвращает qty строкой.

Строки fieldset/legend, явные «Добавить строку», «Удалить строку N»; минимум
одна. Одна исходная receipt_item_id не повторяется, разные строки одного SKU допустимы.
После удаления фокус в ближайшую строку или на добавление. Ошибка сохраняет ввод.
«Сохранить черновик» не отправляет на согласование и не меняет остатки.

Обязательные reason_type (damage/expiry/other) и текст reason. Фотографии
обязательны для damage/expiry, а также если любая исходная партия уже просрочена,
даже при other. Объяснение показывается рядом с причиной и загруженными фото.
Сервер проверяет правило при submit и post: партия может истечь после согласования.
При photo_required на post не предлагать обход сменой причины; обновить документ
и показать разрешённый сервером дальнейший маршрут.

Сначала сохранение черновика, затем явная загрузка фотографий. Применять writeoff
pattern: JPEG/PNG/WebP, максимум 5 активных фото, 10 MiB/20 MP каждое; сервер
декодирует и очищает metadata. Локальный выбор не считается загрузкой. Состояния
выбран → загружается → сохранён/ошибка с retry. Изменение фото только draft.
Authenticated blob preview, никаких token в URL или публичного media; отдельная
ошибка превью, revokeObjectURL при смене документа/прав/unmount. Удаление требует
явного действия и не удаляет аудиторскую историю. При смене прав очистить превью.

## Этапы и роли

Складской автор создаёт/редактирует черновик, отправляет на согласование,
отменяет до проведения в пределах серверных действий. Независимый согласующий
видит исходную приёмку, строки, причину, материалы и историю; собственное
согласование не предлагать. Доступны «Согласовать», «Вернуть на доработку»,
«Отклонить» только при разрешении API. Причина возврата/отклонения обязательна.
Возврат открывает исправление; отклонение/отмена сохраняют исторический документ.

Основной маршрут: «Черновик» → «На согласовании» → «Согласовано» → «Отправлено
поставщику / Проведено» (окончательная подпись по контракту). Согласование само
по себе не уменьшает остатки. Постоянная помощь: «Остатки изменятся только при
подтверждении отправки. Доступность проверяется повторно сервером».
Черновик и согласование не резервируют остатки; показать это явно.

Проведение требует отдельного inline-подтверждения: номер, приёмка, поставщик,
склад, строки и количества; текст «Товар будет списан со склада для возврата
поставщику. Проведённый документ нельзя редактировать или отменить».
Кнопки «Подтвердить отправку» / «Назад». Во время мутации блокировать повтор и
смену контекста. После успеха обновить точные детали, список, справочные остатки;
показать автора/дату и движение. Повтор запроса не добавляет локальный дубль.

## Финансовое состояние

Складской и финансовый статусы показываются отдельно. После проведения при
реальном серверном pending: «Финансовая корректировка ожидает подтверждения»;
пояснение «Отправка товара не изменяет автоматически задолженность и платежи».
«Уведомление финансовой службе создано» показывать только по подтверждённому
серверному факту. Наличие уведомления не означает принятую корректировку.

Суммы, себестоимость, задолженность и финансовые действия показываются только
при наличии соответствующих полей/прав. Отсутствующая цена не равна нулю.
Средневзвешенная стоимость движения не является обещанной суммой возмещения.
Не показывать кнопку «Закрыть финансовую корректировку», если нет реального
контракта подтверждения с проверкой периода и прав. Если он появляется, его
UX и критерии должны быть согласованы отдельно; бухгалтер не редактирует исходный
складской документ. Неразработанный финансовый остаток явно фиксируется в статусе
реализации, а не скрывается за общим бейджем «Завершено».

## Реестр финансовой службы

В существующем FinanceView отдельная секция/представление «Возвраты поставщикам —
ожидают корректировки», только finance.payable.read. Источник — финансовый
GET /finance/supplier-returns, без обращения к складу под чужими правами.
Поля: номер возврата, приёмка, поставщик, дата проведения, валюта и
stock_valuation. Подпись: «Учётная стоимость движения; не сумма возврата денег
и не уменьшение задолженности». Фильтр/пагинация согласно API, состояния
loading/empty/error и retry как у остальных финансовых таблиц.

Детали содержат неизменяемый snapshot и finance_review_status=pending; до
проведения статус null не переводить как «Подтверждено». Read-only реестр,
без кнопки бухгалтерского подтверждения. Уведомление ведёт к доступной
финансовой записи, а не требует предоставления складских прав. Приватные фото
для финансового просмотра доступны только через отдельно авторизованный finance
endpoint, когда он включён BE в контракт: существующий warehouse download_url
не считать таким разрешением и не использовать для обхода warehouse scope.
Пока finance-фотомаршрута нет, не рисовать недействующую кнопку просмотра.

Дополнительные ожидаемые FE-файлы: секция в FinanceView.tsx либо отдельный
SupplierReturnFinanceQueue.tsx, API/DTO и словарь четырёх локалей. Финансовый
реестр должен быть описан в отчёте как уведомление и очередь ожидания, а не
выполненная бухгалтерская корректировка.

## Ошибки и асинхронность

Loading: aria-busy и локализованный текст. Empty различает отсутствие документов,
пустой фильтр, отсутствие проведённых приёмок и отсутствие назначенного склада.
Forbidden очищает недоступные детали/формы/действия/превью, обновляет каталог;
запоздалый ответ не восстанавливает права. Conflict обновляет точный документ и
доступность, объясняет изменившееся количество/этап; не проводит повторно
автоматически. При network failure сохранённый документ заново читается перед
повтором потенциально завершённой мутации. Не заявлять, что операция точно
не состоялась только из-за потери ответа.

Generation/request invalidation на смену склада, фильтра, страницы, документа,
закрытие и unmount. Ошибка одного контекста не перекрывает другой. 400 привязать
к полям по стабильным кодам и перевести; raw backend English не использовать
как единственный пользовательский текст. Ошибка role=alert, успех role=status.

## Layout, доступность и локали

Сохранить WMS max-w-7xl; padding 16px mobile / 24px desktop, gap 16–24px.
Заголовок 24px bold, секции 18px semibold, текст 14–16px. Одна колонка <640px,
две ≥640px; длинная причина на всю ширину. При 360px карточки и формы укладываются
в viewport; min-w-0/break-words для номеров, поставщиков и SKU. Никакого усечения
критичного количества или статуса. Таблица прокручивается в своём контейнере.

Tokens: bg-white dark:bg-slate-900; text-slate-950 dark:text-slate-100;
secondary text-slate-600 dark:text-slate-300; border-slate-300 dark:border-slate-600;
primary bg-blue-700 text-white hover:bg-blue-800; ошибки text-rose-800
dark:text-rose-200; warning text-amber-900 dark:text-amber-200. Статусы содержат
текст. Цель: текст 4.5:1, focus/значимые границы 3:1 в обеих темах; требуется
инструментальная проверка фактических сочетаний FE, здесь она не заявляется.

Нативные buttons/inputs/selects; labels, required, aria-invalid/describedby;
видимый focus 2px offset, hit area ≥44px. Открытие документа переносит фокус на
h2 tabIndex=-1; закрытие возвращает исходному триггеру или заголовку раздела.
Inline-form предпочтительна. Если dialog — существующий AccessibleDialog с
trap/Escape/return focus. Не перехватывать Enter как необратимое проведение.

Полный словарь RU/KY/zh-Hans/zh-Hant: заголовки, строки, причины ошибок,
статусы, подтверждения, aria и пустые состояния. Даты/числа Intl выбранной
локали; коды SKU и номера документов не переводятся. Имена из мультиязычного
DTO с понятным fallback. Не склеивать предложения из фрагментов; длинные RU/KY
и обе китайские письменности проверяются отдельно.

Ожидаемые файлы FE: frontend/src/components/SupplierReturnView.tsx,
frontend/src/lib/supplier-return-i18n.ts, DTO в types/index.ts, API в lib/api.ts,
интеграция в WarehouseView.tsx. Не менять глобальные tokens/зависимости без причины.
BE владеет контрактом, схемой, миграциями и правилами; UX production-код не меняет.

## Критерии приёмки и открытые зависимости

1. Создание только из доступной проведённой приёмки; чужая приёмка не выдаётся;
   склад/поставщик/происхождение неизменны; повторный SKU из разных исходных строк
   не теряет идентичность. Старые source-значения не сохраняются после смены.
2. Независимое согласование/возврат/отклонение/отмена и история соответствуют
   allowed_actions; до проведения остатки не меняются; post отдельно подтверждён.
3. Исчерпанный лимит возврата и нехватка текущего остатка дают разные понятные
   ошибки; прямой запрос проверяется backend. Дубли и гонки не обходят лимиты.
4. Проведение создаёт точное движение; повтор/reload не дублирует выбытие;
   движение открывает документ вне первой страницы по ID.
5. Уведомление/ожидание финансового подтверждения отражаются по API; нет ложного
   уменьшения долга, возмещения или полного финансового закрытия. Стоимости скрыты
   без прав. Возврат порчи/просрочки проходит только с требуемыми сохранёнными фото.
6. Проверить 400/403/409/network, быстрые переключения, stale responses, повторные
   клики, empty, keyboard-only, 360px, обе темы, четыре локали и фокус из ledger.
7. Отчёт отделяет фактические browser/axe/контрастные тесты от инспекции кода.

Оставшиеся финансовые решения: кредит/возврат денег по оплаченным сверкам,
валютные разницы и корректировки закрытого периода. Pending-реестр их не
реализует. Документ подготовлен по инспекции ТЗ и исходников, контракт сверён
с BE/TL; браузерная проверка нового экрана ещё не проводилась.
