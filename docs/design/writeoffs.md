# Списания с фотографиями: handoff

Дата: 31.10.2026. Источники: Б7.7/Г.7 и Г.13.9 объединённого ТЗ;
`WarehouseView.tsx`, `TransferView.tsx`, `docs/design/warehouse.md` и
`docs/design/transfers.md`. Владелец документа — Designer. Frontend реализует
экран по этому handoff и утверждённому API `docs/api/writeoffs.md`.
Backend-контракт согласован Tech Lead: global `reason`, decimal qty до 3 знаков,
уникальность `(sku, location, batch)`; JPEG/PNG/WebP, до 5 активных фотографий,
до 10 MiB каждая, до 20 мегапикселей. Изображения декодируются и очищаются сервером.

## Назначение и пользовательский маршрут

Кладовщик фиксирует порчу/истечение срока или другую разрешённую причину,
выбирает товар из своего склада, прикладывает фотографии и передаёт документ
на независимое согласование. Утверждение не списывает товар автоматически:
кладовщик отдельно подтверждает проведение. Только проведённый документ
уменьшает физические остатки и партии и создаёт прослеживаемое движение.

Маршрут: «Черновик» → «На согласовании» → «Согласовано» → «Проведено».
Возврат с причиной снова открывает черновик; отклонение окончательное.
Отмена допускается до проведения. Согласующий не утверждает собственный
документ. Складской scope и разрешённые действия определяет сервер.
Создание, загрузка фотографии и отправка на согласование — отдельные действия.
Не превращать выбор локального файла в признак успешно загруженной фотографии.

Постоянное пояснение: «Черновик и согласование не изменяют и не резервируют
остатки. Доступность проверяется при проведении». Не называть предлагаемое
количество уже списанным до статуса `posted`.

## Размещение и состав компонентов

Новая кнопка представления «Списания» внутри существующего WMS. Использовать
обычные кнопки `aria-pressed`, без неполного ARIA tablist. Общий выбор склада
сохраняется. Вкладка видна при серверном праве чтения списаний; отсутствие
назначенных складов показывает объяснение без формы создания.

Предпочтительны отдельный `WriteoffView`, небольшая секция/компонент фотографий
и отдельный `writeoff-i18n.ts`. Родительский `WarehouseView` не должен хранить
большую форму или превращаться в универсальный редактор документов.

Список: номер; склад; причина; статус; дата; число фотографий; «Открыть».
Статус-фильтр и пагинация только по поддерживаемым параметрам API. Desktop —
семантическая таблица с caption и заголовками `scope=col`. Mobile —
`article + dl`, явная кнопка открытия, без кликабельности всей карточки.

Детали inline: заголовок с номером; причина/комментарий; автор и этапы
согласования/проведения с датами; строки товара; фотографии; доступные действия;
история. Для исторического документа без данных этапа показывать «Нет данных»,
а не выдуманного проверяющего. Количество предложено/списано определяется статусом.
Себестоимость скрыта целиком при отсутствии поля, не подставлять ноль.

Движение `stock_writeoff` открывает точный документ через lookup ID, даже если
его нет на первой странице списка. Заголовок деталей получает фокус.
При неуспешном открытии retry повторяет тот же ID; смена склада/фильтра,
закрытие деталей или создание нового документа сбрасывают устаревшее намерение.

## Форма черновика

Длинная inline-форма. Номер документа (`writeoff_no`), выбранный склад,
обязательная общая причина (`reason`) свободным текстом. Отдельные коды причин
или комментарий API не вводит. Номер и склад после создания неизменяемы:
в edit показывать их read-only/disabled, исправляются reason и строки.
Для другого склада/номера — отмена до проведения и новый документ.

Строки: SKU/название, ячейка («Без ячейки» для null), партия («Без партии»
только для доступного непартийного остатка), срок выбранной партии, количество.
Срок не редактируется как новая дата. Выбор только из разрешённого каталога;
не предоставлять произвольный ввод ID или чужой ячейки. При смене склада/SKU/
ячейки сбросить зависимые значения партии. Справочный физический доступный
остаток и количество в выбранной партии показаны рядом; это не резерв.

Количество — положительная decimal-строка до 3 десятичных знаков, как в складском
балансе. Пустой ввод не превращается в ноль. Уникальна комбинация SKU/ячейка/партия:
тот же SKU в других ячейках или партиях разрешён в одном документе. Не переносить
ограничение «один SKU на документ» из перемещений. Повтор одинаковой комбинации
объяснить рядом с формой; до 100 строк согласно подтверждённому каталогу API.

Строка — `fieldset/legend`, нумерация, «Добавить строку», «Удалить строку N»;
минимум одна. После удаления фокус в ближайшую оставшуюся строку или «Добавить».
«Сохранить черновик» не выполняет submit на согласование. При успехе открыть
сохранённые детали и секцию «Фотографии». При ошибке сохранять введённые поля.

## Фотографии и приватность

Фотографии прикрепляются к сохранённому черновику. До сохранения формы показать
«Сохраните черновик, затем добавьте фотографии». В деталях доступный сервером
счётчик фото; у нулевого значения заметное текстовое пояснение:
«Для отправки на согласование нужна хотя бы одна загруженная фотография».

Нативный input `type=file` с постоянным label «Добавить фотографию» и допустимыми
`accept` JPEG/PNG/WebP согласно API. `capture=environment` допустим как подсказка
мобильной камере, но загрузка из галереи должна оставаться доступной. Рядом
видимая подпись «JPEG, PNG или WebP; до 10 MiB; не более 5 фотографий» и
пояснение лимита 20 мегапикселей в помощи/ошибке. Frontend предварительно проверяет размер/формат для UX;
серверная проверка фактического содержимого авторитетна. SVG и переименованный
нефотографический файл не считаются допустимой фотографией.

Выбранный файл: имя, размер, локальное превью по возможности и явная кнопка
«Загрузить». Состояния: выбран локально → загружается → успешно сохранён / ошибка.
Не добавлять failed upload в число обязательных фото. При ошибке сохранять
выбор для retry; после успеха сбросить input. При нескольких файлах API может
требовать последовательную загрузку; показывать индивидуальный результат,
не заявлять успех всех при частичном сбое.

Загруженные фотографии: компактный список с именем/размером и явной кнопкой
«Показать фотографию» (ленивый authenticated blob preview), при разрешении
«Убрать из черновика фотографию N». Автоматическая загрузка всех файлов не
требуется; ошибка одного превью не блокирует другие. Backend снимает фото из
активных материалов черновика, сохраняя приватную аудиторскую историю.
Удаление только в черновике по серверному `allowed_actions`; после submit
фото остаются видимыми, но не заменяются и не удаляются. Возврат в черновик
снова разрешает поддержанные API операции. После отказа/проведения фотографии
не скрывать и не показывать недействительную кнопку удаления.

Доступ к изображению — авторизованный API fetch с bearer → blob → object URL.
Не использовать публичный media URL, token в query string, localStorage URL
или прямой `<img src=api/download>` без авторизации. При загрузке изображения
показать локальную загрузку, при ошибке — retry этой фотографии. После 401/403
очистить прежние превью и действия. Не удерживать старые чувствительные blob
при смене документа/склада, выходе или отзыве прав. `URL.revokeObjectURL` при
замене, удалении и unmount, также очистить локальные превью выбранных файлов.

Миниатюры не обязаны загружать все полноразмерные фото одновременно: явное
действие загрузки/открытия допустимо. Превью имеет alt «Фотография списания N»;
имя файла рядом не должно быть единственной доступной подписью действия.
Если полноразмерное фото открывается внутри dialog — только существующий
`AccessibleDialog` с trap, Escape и возвратом фокуса. Для этого этапа допустим
inline-preview с ограничением высоты и `object-contain`, без нового lightbox.

## Согласование и проведение

Точный `allowed_actions` серверный: `edit`, `upload_photo`, `delete_photo`,
`submit`, `review`, `post`, `cancel`.
Кнопка submit недоступна без сохранённой фотографии и обязательной причины;
текстом объяснить, что добавить. Сервер также обязан отклонять прямой запрос.

Согласующий видит строки и фотографии до решения. Действия «Согласовать»,
«Вернуть на доработку», «Отклонить». Для возврата/отклонения обязательная причина
с label, `aria-invalid` и сохранением ввода при ошибке. Самосогласование не
предлагать. Решение не списывает остатки.

Проведение — отдельное inline-подтверждение: номер документа, перечень/общее
количество, причина, предупреждение «Количество будет списано со склада.
Проведённый документ нельзя редактировать или отменить». Явные «Подтвердить
списание» и «Назад». Повторный клик блокируется на время запроса. Успех
обновляет точные детали, список и справочные остатки, а кнопка post исчезает.
После проведения показывать дату/автора и номер движения/ссылку при наличии API.

Отмена до проведения имеет отдельное подтверждение; фото и история сохраняются.
Не рисовать кнопки исправления проведённого списания, возврата товара или
финансовой корректировки, если эти процессы ещё не реализованы.

## Ошибки, асинхронность и доступность

Начальная загрузка — локализованный текст и `aria-busy`; empty только после
ответа. Различать отсутствие записей, пустой фильтр и отсутствие назначенного
склада. Успех — `role=status`, ошибки — `role=alert`, явный retry. Ошибки
ввода связаны с полями через `aria-invalid` и `aria-describedby`.

403 очищает недоступные детали/формы/фото/actions, обновляет каталог. Запоздалый
200 прежнего каталога не возвращает права. 409 обновляет точный документ и
доступность, не повторяет проведение автоматически и не оставляет устаревшие
actions; показывать отдельное понятное объяснение недостатка/конфликта партии.
500/сеть сохраняют ввод и намерение exact-ID для retry. Stale response после
смены фильтра/страницы/склада/закрытия не открывает старый документ.

Во время мутации/загрузки фотографии блокировать повтор действия и смену
склада/вкладки/документа. Не делать весь список live region. После открытия
деталей или формы фокус на заголовок `tabIndex=-1`; после закрытия — на trigger,
если он существует, иначе на устойчивый заголовок списка. После удаления фото
фокус на следующий доступный элемент/«Добавить фотографию».

Нативные кнопки/controls, связанные labels, клавиатурная доступность всех
действий. Минимальная цель 44×44px на mobile. Focus-visible ring 2px с offset.
Номер, статус и причина не передаются одним цветом. Pending-состояния не
снижают контраст всей формы непрозрачностью.

## Layout и tokens

Сохранить max-w-7xl и оболочку WMS: padding 16px mobile/24px desktop;
вертикальные интервалы 16–24px; h2 раздела 20px bold, h3 секции 18px semibold,
основной текст 14–16px. Формы одна колонка <640px, две ≥640px; причина и
фотографии на всю ширину. Фото-grid 1 колонка mobile, 2 ≥640px, 3 ≥1024px,
миниатюры в ограниченной области с `object-contain`; не обрезать доказательство
порчи необратимым crop. Длинные имена/номера/комментарии — `min-w-0 break-words`.
Desktop таблица прокручивается только в своём контейнере, mobile карточки
не выходят за 360px viewport.

Tokens проекта: `bg-white dark:bg-slate-900`, `text-slate-950 dark:text-slate-100`,
secondary `text-slate-600 dark:text-slate-300`, border
`border-slate-300 dark:border-slate-600`. Primary `bg-blue-700 text-white`, hover
`bg-blue-800` без конфликтующего neutral hover. Ошибка `text-rose-800
dark:text-rose-200`, предупреждение `text-amber-900 dark:text-amber-200`.
Текст ≥4.5:1, границы/фокус ≥3:1 в обеих темах.

## Локали, файлы и приёмка

Все новые подписи, статусы, ошибки, сообщения upload/download, лимиты,
подтверждения, alt/aria и empty states имеют явные RU/KY/zh-Hans/zh-Hant строки.
Traditional Chinese не копируется из simplified. Числа/даты/размеры — через
Intl выбранной локали. Тексты бизнес-причины/имена файлов сохраняются исходными,
не выдавать отсутствующий перевод за локализованное содержимое. Ошибки API
локализуются по стабильному code, не по английскому message.

Ожидаемые frontend-файлы: новый `components/WriteoffView.tsx`, при необходимости
`WriteoffPhotos.tsx`, `lib/writeoff-i18n.ts`; добавления DTO в `types/index.ts`,
методов в `lib/api.ts`; интеграция вкладки/exact source lookup в
`components/WarehouseView.tsx`. Navbar/page не требуют новой верхней навигации.
Общие tokens/зависимости менять только по конкретной согласованной необходимости.

Критерии приёмки:

1. Кладовщик видит только свой склад, создаёт документ с причиной/ячейкой/партией,
   сохраняет черновик; физический остаток до проведения не меняется.
2. Без реально загруженной фотографии submit недоступен и прямой API отвергается.
   Неверный формат/слишком большой файл объясняются локализованно; failed upload
   не засчитывается как фото; приватное изображение недоступно чужому пользователю.
3. Независимый согласующий изучает фото и строки, возвращает с причиной;
   автор исправляет/дополняет фото только в черновике и подаёт снова.
4. Утверждённый документ проводится отдельно; после reload статус/остаток/история
   сохраняются, повтор не дублирует движение. Недостаток или конфликт партии
   не оставляет частичного списания.
5. Фотографии просматриваются в approved/posted; удалить/подменить их нельзя.
   Отзыв доступа очищает изображения и действия, старый ответ их не восстанавливает.
6. Ссылка движения открывает exact-ID, retry после 500 работает вне первой
   страницы; задержанный ответ после смены контекста не открывает старые детали.
7. Все четыре локали, 360/1440px, обе темы, клавиатура/фокус/alt/ошибки проверены;
   исполнитель отдельно указывает реальные browser/axe проверки и их ограничения.
8. Frontend lint/TypeScript/build и backend сценарии проходят; независимый reviewer
   оценивает код. Сам handoff не является утверждением, что проверки уже выполнены.
