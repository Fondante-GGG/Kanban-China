# KPI: handoff для реализации

Дата: 31.10.2026. Источники: Б7.8 и Г.8 объединённого ТЗ, текущие `kpi_views.py`, `KpiTaskModel`, `Navbar`, `ProcurementView`, `EmployeeDirectoryView`, `AccessibleDialog`.

## Назначение и границы

Сотрудник видит свой период оценки, отправляет самооценку, знакомится с утверждённым результатом. Руководитель назначает оценки разрешённым сотрудникам и оценивает их. Вышестоящий проверяющий утверждает результат, если backend предоставляет отдельный этап и полномочие. История завершённых оценок доступна без возможности редактирования.

На момент исходной инспекции backend поддерживал только месяц/квартал и непосредственное manager→confirmed. Согласованный Tech Lead контракт этого этапа расширяет его: month|quarter|year, веса шаблона суммой 100, scoped assignees, display names/allowed_actions/history, manager→senior_review, director approve|return, отдельный archive timestamp. Приведённые ниже оговорки о недоступном API относятся только к функциям сверх этого согласованного контракта. Автоматические формулы, передача премий, напоминания и построчные баллы в этот этап не включены; не изображать их работающими.

## Структура экрана

Добавить рабочий раздел «KPI» в desktop и mobile навигацию при `kpi.read` либо доступе директора. Заголовок `h1`, короткое пояснение о доступном сотруднику объёме данных. Справа «Обновить», для `kpi.manage` — «Назначить оценку» и «Создать шаблон».

Под заголовком — обычные кнопки переключения представления с `aria-pressed`: «Оценки», «Архив», для управляющего «Шаблоны». Не применять ARIA tabs без полного keyboard tablist поведения.

«Оценки»: фильтры год/период/статус; таблица «Сотрудник», «Шаблон / должность», «Период», «Этап», «Самооценка», «Оценка руководителя», «Итог», «Действие». Архив — то же представление для записей с отдельным timestamp архивирования. Явная кнопка «В архив» доступна через allowed_actions только после confirmed + acknowledged_at; само ознакомление не архивирует запись автоматически. Утверждённые без ознакомления остаются в активных для действия сотрудника.

Каждая оценка открывается явной кнопкой «Открыть оценку». Детали показывают доступные данные шаблона/периода, баллы и этапы в нумерованном списке, время ознакомления. Показывать отдельный этап «Проверка вышестоящим руководителем» для senior_review. Исторические confirmed без review event не подписывать как отдельно проверенные вышестоящим руководителем.

## Компоненты и формы

1. `KpiView`: загрузка, представления, фильтры, состояния доступа.
2. Список/таблица оценок и семантический список этапов. Статус — текст плюс цвет, без зависимости только от цвета.
3. Форма назначения: сотрудник из разрешённого сервером списка, активный шаблон с должностью/циклом, год, номер месяца 1–12 либо квартала 1–4, либо годовой период согласно утверждённому backend значению. Ни один сотрудник не выбирается вводом произвольного ID. Если нет разрешённых сотрудников/шаблонов — пояснение и закрытая форма.
4. Форма шаблона: название, код должности, цикл; динамические строки с названиями на RU/KY/ZH, весом и формулой. Постоянные label, `fieldset/legend` для показателя; «Добавить показатель», «Удалить показатель N». Минимум одна строка. Веса показывать как проценты, сумму рядом. Сумма весов обязательна 100 согласно контракту; грамматику формулы подтвердить по backend-контракту; не вычислять/исполнять формулы на клиенте. Если backend хранит только текст формулы, поле подписать «Формула (описание)», без обещания автоматического расчёта.
5. Форма оценки: текущие баллы, число 0–100 с допустимой сервером точностью, явная кнопка «Отправить самооценку» / «Отправить оценку руководителя». До submit — пояснение о переходе на следующий этап. Использовать серверные правила для допустимости и ошибок. Не допускать подмены пустого значения нулём.
6. Ознакомление: результат и пояснение «Подтверждаю, что ознакомился с результатом», явная кнопка «Подтвердить ознакомление». После успеха — неизменяемая дата/время вместо кнопки. Не оформлять это как согласие с оценкой.
7. Senior-review по согласованному контракту: только в разрешённом состоянии — кнопка утверждения и форма возврата с обязательным комментарием. История показывает автора, время, действие и комментарий. Утверждать может директор, отличный от автора manager-score; решающим остаётся allowed_actions, не локальная догадка о роли. При возврате показать текст следующего этапа согласно ответу backend.

## API и разрешения: обязательная координация

Frontend не должен запрашивать кадровый реестр ради отображения собственной оценки: HR-доступ независим от KPI. Согласованный GET tasks предоставляет отображаемые имя сотрудника, имя/цикл шаблона, связь с текущим пользователем либо `allowed_actions`. GET templates теперь доступен read/manage, но UI не должен блокировать список оценок на его ошибке; используйте display fields задач. Snapshot показателей согласовывать отдельно при необходимости. Для назначения используйте GET /kpi/assignees; права `kpi.manage` сами по себе не должны раскрывать весь HR-реестр.

Ожидаемые действия: `self_score`, `manager_score`, `review` approve|return по именам actions из окончательного DTO, `acknowledge`, `archive`. Сервер подтверждает их на каждом запросе. Только владелец отправляет самооценку/ознакомление; руководитель работает с разрешённым отделом; пользователь с read не видит управляющих форм. Директор не подтверждает ознакомление за сотрудника. `acknowledged_at` — дополнительный факт при `confirmed`, не отдельный статус текущего API.

403: локализованное сообщение доступа и отсутствие действий; 409/конфликт этапа: сохранить введённое значение, обновить серверную запись и объяснить смену этапа; сеть/500: сообщение и повтор. Не показывать сырой английский backend error как единственный пользовательский текст. Ошибки валидации сопоставлять с полями. Не переходить в следующий этап оптимистически.

## Layout и визуальные токены

Контейнер `max-w-7xl`, padding 16px mobile / 24px от sm; вертикальные секции с шагом 16–24px. Заголовок 20–24px semibold/bold, основной текст 14–16px; подписи/метаданные не меньше 12px. Формы: gap 12–16px, связанные label/input gap 4–6px.

Desktop ≥1024px: таблица, фильтры в ряд с переносом. Планшет 640–1023px: фильтры в две колонки, таблица только внутри контейнера прокрутки с видимым указанием возможности прокрутки. Mobile <640px: записи вертикальными `article`/`dl`, метки рядом со значениями; действия на отдельной строке, без горизонтальной прокрутки страницы. Динамическая форма шаблона на mobile одна колонка; длинный редактор inline в основной странице предпочтительнее модального окна. Диалог только для короткого назначения/оценки/ознакомления; max-height с внутренней прокруткой и видимой кнопкой закрытия.

Сохранить Tailwind slate/blue tokens проекта. Фон `bg-white dark:bg-slate-900`, основной текст `text-slate-950 dark:text-slate-100`, вторичный `text-slate-600 dark:text-slate-300`, границы `border-slate-300 dark:border-slate-600`. Primary `bg-blue-700 text-white` с различимым hover; ошибки `text-rose-700 dark:text-rose-300`, успех `text-emerald-800 dark:text-emerald-200`. Контраст текста ≥4.5:1, границ/фокуса ≥3:1. Не снижать opacity всего текста статуса; disabled действие имеет явное пояснение причины при необходимости.

## Состояния и доступность

- Начальная загрузка: локализованный текст, `aria-busy` у содержимого; пустое состояние появляется только после ответа.
- Пустое: различать «Оценки ещё не назначены», «По фильтрам ничего не найдено», «Архив пуст». Для управляющего доступна целевая кнопка назначения.
- Сохранение: блокировать повторное действие только соответствующей формы, текст «Сохраняем…», `aria-live=polite` для результата.
- Ошибка: `role=alert`, видимый retry; не очищать введённую форму при неуспехе.
- Все input/select/textarea имеют связанные label; ошибка через `aria-describedby` и `aria-invalid`. Нативные button и controls, hit target минимум 44×44px mobile.
- Focus-visible outline/ring 2px с offset. Таблица содержит caption, заголовки `scope=col`; строки не являются единственной кликабельной целью.
- Dialog: `AccessibleDialog` с возвратом фокуса, trap и Escape. Перед использованием проверить начальное фокусирование и стабильность `onClose`, чтобы rerender не сбрасывал введённые данные/фокус. При закрытии несохранённого текста не терять данные без явного действия пользователя.
- Статусы и действия сообщаются экранному диктору один раз после ответа; не делать весь часто обновляемый список live region.

## Четыре локали

Все UI labels, этапы, пустые/ошибочные состояния, aria-label, сообщения валидации и действия обязательны для `ru`, `ky`, `zh-Hans`, `zh-Hant`. Использовать отдельный типизированный `kpiTranslations` словарь; Traditional Chinese — самостоятельные строки, не копия simplified. Имена бизнес-данных: RU/KY/ZH с понятным fallback на исходное значение; отсутствие перевода не должно менять язык всей оболочки. Даты/время форматировать через Intl для выбранной локали; баллы форматировать согласно locale, API передаёт десятичную строку. Не выводить коды статусов/ID как единственную подпись. Текст действия допускает перенос; фиксированную ширину русских подписей не задавать.

## Приёмка UI

1. Сотрудник без HR/manage видит собственную оценку с читаемыми именами/периодом, отправляет self-score, затем после утверждения подтверждает ознакомление.
2. Управляющий с разрешённым scope создаёт валидный шаблон, назначает оценку из scoped selector, оценивает доступного сотрудника. Отсутствие полномочий скрывает формы, API отказ отображается корректно.
3. После acknowledgement результат и время сохраняются после reload, повтор не создаёт локальную дублированную запись; архив читается без редактирования.
4. На mobile 360px, tablet и desktop нет выхода контента за viewport; все действия доступны с клавиатуры, modal фокус возвращается на trigger.
5. Светлая/тёмная темы и все четыре языка покрывают весь новый UI, включая ошибки и aria labels.
6. Загрузка, empty, validation, network fail, forbidden и concurrent state change проверены; lint/tsc/build пройдены и результаты указаны точно.
7. Senior stage и история проходят отдельный сценарий: manager score → senior_review → другой director approve → owner acknowledge → archive; возврат требует комментария. Автоматические KPI и премии остаются отдельными требованиями; этот экран сам по себе не закрывает всё Г.8.
